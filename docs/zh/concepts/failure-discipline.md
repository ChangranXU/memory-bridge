# 失效纪律

memory-bridge 建立在一个核心原则上：**故障的记忆系统绝不能改变智能体的行为。** 桥接层采用失效封闭设计——当记忆关闭或损坏时，智能体的运行与原始版本完全一致。

## 核心规则

{% hint style="danger" %}
这些规则是不变量，不是指南。违反它们就是 bug。
{% endhint %}

1. **除非 `strict: true`，否则不会向智能体循环抛出异常**——故障被容纳、计数（`backend_errors`）并记录日志。
2. **`note_recall` 永不抛出异常**——可观测性绝不能掩盖模型异常。
3. **标注故障退化为无追踪的原始行为**——它们永不改变记忆状态或模型流量。
4. **`run()` 内的严格启动失败仍会干净地 finalize**——失败前打开的任何 SQLite 句柄都会被正确关闭。

## 熔断器

三个独立的熔断器防止故障失控：

| 熔断器 | 配置键 | 默认值 | 作用域 |
|---|---|---|---|
| 提取 | `extract_max_consecutive_errors` | `3` | 停止周期性提取；最终刷新始终运行。 |
| 查询改写 | `rewrite_max_consecutive_errors` | `3` | 停止改写器 lane；保留旧查询。 |
| 标注 | `annotate_max_consecutive_errors` | `3` | 停止该 episode 的标注 I/O；记忆行为不变。 |

将提取或改写熔断器设为 `0` 可将其禁用（永远重试）；标注熔断器至少为 1。每次成功操作后熔断器重置。

## 按层的故障容纳

### 后端故障

当 `strict=false`（默认）时，后端操作的任何异常会被：

1. 捕获并记录日志
2. 计入 `backend_errors`
3. 智能体继续执行，如同记忆未返回任何内容

模型永远看不到记忆故障的证据。

### 提取故障

失败的提取计入 `extraction_errors` 并触发熔断器。提取调度在后续步骤继续——错过的提取边界会在下一个干净步骤补上。

### 召回故障

失败的搜索同时计入 `search_errors`（每操作粒度）和 `backend_errors`（信封粒度）。该步骤的召回返回 `None`，因此不注入记忆消息。失败的搜索永不被缓存——脏标记保持设置状态，下一步重试。

### 标注故障

标注是纯可观测性。每种故障模式精确降级：

| 条件 | 效果 |
|---|---|
| 启动 post 超大（413） | 该操作不被追踪 |
| 恢复冲突（409） | 该 episode 的 memory lane 被禁用 |
| 操作中被拒绝 | 该操作不再发送事件；整个会话的 memory lane 追踪被禁用 |
| main-lane cursor 不可读 | 该 delivery 被跳过 |
| 重试耗尽 | 该 episode 的标注 I/O 停止 |

## 凭据安全

凭据在每一层都受到保护：

* Pydantic 字段标记为 `exclude=True, repr=False`
* 只有脱敏后的 URL 才会出现在产物和日志中
* 用户信息、查询字符串和片段被移除
* 轨迹 ID 被替换为其 16 个十六进制字符的 SHA-256 哈希前缀
